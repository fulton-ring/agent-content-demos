# Keeping a retired Dynamics GP system's history queryable

This demo asks whether a company leaving Dynamics GP can copy the old system's history into a database its team and auditors can query, prove the copy against the old system's reports, and then turn the old system off. It does that end to end on a synthetic GP company database running in SQL Server:

1. builds the source database (three closed fiscal years and nine months of an open one) with GP's real table and column names,
2. copies every table into a DuckDB file and a folder of Parquet files, using a login that can only read,
3. runs the trial balance, receivables and payables agings, and customer and vendor history reports on the source and on the archive, and compares every value,
4. shuts SQL Server down and answers a set of auditor questions from the archive alone.

Answer from this run: **yes, on this data.** All 58,888 rows in 18 tables copied with matching row fingerprints. 23,040 report values were compared between source and archive. Every agings and history value matched, and the agings tie to the AR and AP control accounts at all 45 period ends. The trial balance had one difference, which we planted on purpose: a journal entry that GP's summary table never received. The reconciliation found it and named the entry. The archive answers the auditor queries after the server is gone.

Proposal card: [Can a retired Dynamics GP or NAV system's history stay queryable after the old software is turned off?](https://app.notion.com/p/3f8cc69045cb8143a95ad63302778ba5) · Issue: [#5](https://github.com/fulton-ring/agent-content-demos/issues/5)

## Run it

You need Docker, Python 3.10 or newer, `openssl` and `bc`. The first run downloads the SQL Server 2022 image, which is about 1.5 GB.

```sh
./run.sh
```

The script starts SQL Server 2022 Developer edition in a container, builds the database, exports it, reconciles, removes the container, then runs the saved queries. It writes:

- `results/reconciliation.md`: the full source-against-archive comparison
- `results/samples/`: auditor query outputs, produced after the source was removed
- `results/timings.md`
- `build/`: the archive itself (`gp_archive.duckdb`, `parquet/`, `manifest.json`) and every report as CSV (not committed)

After a run, query the archive with no database server at all:

```sh
.venv/bin/python query.py trial_balance year=2025 period=6
.venv/bin/python query.py vendor_payment_history vendor=V0001
.venv/bin/python query.py open_ar_at_date as_of=2024-12-31
.venv/bin/python query.py journal_entries_by_user user=sa from=2023-01-01 to=2026-09-30
.venv/bin/python query.py document_trail document=INV0000701
.venv/bin/python query.py unusual_journal_entries from=2025-01-01 to=2025-12-31
```

Add `--parquet` to read the Parquet files instead of the DuckDB file. The script also checks that both give the same trial balance. Add `--csv out.csv` to save a result. The queries are plain SQL files in `queries/`, so anyone with DuckDB, or any tool that reads Parquet, can run or change them.

## Where the data comes from

All of the data is synthetic, generated by `source/generate.py` from a fixed seed, so every run builds the same database. We did not use Microsoft's sample companies:

- **Fabrikam (GP's sample company, the TWO database)** is created from inside a licensed GP installation ("Add sample company data" in GP Utilities). We found no licence term that allows publishing the data, and no official standalone download. The Microsoft Business Solutions licence terms we could read forbid publishing "the software for others to copy". [Microsoft Learn: reinstall the sample company](https://learn.microsoft.com/en-us/dynamics-gp/installation/uninstall-or-reinstall-sample-company)
- **CRONUS and Contoso (NAV and Business Central)**: the AL source of Business Central's demo data tool is MIT-licensed in [microsoft/BCApps](https://github.com/microsoft/BCApps), but the generated company database is a different thing, and Microsoft's docs say to add the demo apps to a company in a paid or trial subscription. Shipping a CRONUS database backup in a public repo is at best unclear, so we didn't.

The generated company keeps calendar fiscal years. 2023 to 2025 are closed, with journal lines in `GL30000` and period summaries in `GL10111`. 2026 is open through September, in `GL20000` and `GL10110`. It has 22 accounts, 60 customers and 24 vendors. Every receivables and payables document posts its journal lines the way GP posting does, and year-end close brings balance sheet accounts forward and closes profit and loss into retained earnings. It also includes what makes real history awkward:

- credit memos and two-part payments applied to invoices
- five bounced customer payments, voided and replaced
- two lost vendor checks, voided and reissued
- unapplied on-account payments and a handful of invoices that were never paid
- fully paid documents moved to the history tables (`RM30101`, `PM30200`) while the rest stay open
- GP's fixed-width `char` columns, padded with trailing spaces
- journal entries posted by `sa`, on a weekend, and for round amounts

One problem is planted on purpose. In 2026, journal entry 13179 ("Office furniture reclass", 12,345.67) is in the journal lines, but its update to the account summary table was "lost", as an interrupted posting can leave it. GP's own trial balance reads the summary table.

**Trial balance by period.** Total debits and credits agree for all 45 periods except May 2026. There the source shows 2,237,670.41 and the archive 2,250,016.28, a difference of 12,345.67 on each side. The reconciliation searched the archive's journal lines for the difference and found journal entry 13179, "Office furniture reclass", posted by GL.ACCT on 2026-05-14: debit 000-1500-00, credit 000-6300-00, 12,345.67. The other 18 differing values are the same amount carried into the beginning and ending balances of June to September for those two accounts. The ledger balances on both sides; the source's summary just never got that entry. On a real system this would show up as GP's trial balance disagreeing with its own detail, which is what GP's financial Reconcile utility exists to repair. It needs fixing before the old system is switched off, or the archive and the last printed trial balance will disagree forever. (The full per-period table is in `results/reconciliation.md`.)

## How a controller would do this on a real GP system

1. Ask IT for a SQL login with read access (`db_datareader`) to the GP company database. Nobody needs to install anything on the GP server.
2. While GP is still running, print or export GP's own Trial Balance, Historical Aged Trial Balance (receivables and payables) and vendor and customer summaries for each year-end and the go-live date, and keep them as PDFs alongside the archive.
3. Run the export against the company database, then run the same reports from the archive and compare them with step 2 and with each other. Here, `reconcile.py` does the comparison; on a real system the source side would be GP's report output, not our SQL.
4. Explain every difference before shutdown. In this run the only one was a summary table that didn't match its detail.
5. Keep the DuckDB file and the Parquet folder with the manifest (row counts and fingerprints) somewhere backed up, and give auditors the saved queries.

## What this doesn't show

- **It isn't real GP.** No GP installation was involved. The source "reports" are our SQL against the tables GP's reports read, not output from GP's report writer. The schema is a subset of GP's columns, written from GP's table and column names; we haven't checked it column for column against a live GP company database. A real database has hundreds of tables, and the export would copy them all (it copies whatever is in `dbo`), but we only reconcile the core ones.
- **The aging comparison checks the copy, not the logic.** Source and archive run the same aging logic in two SQL dialects, so agreement proves the archive holds the same data and can reproduce the report. It doesn't prove the logic matches GP's Historical Aged Trial Balance on edge cases (GP's own report has options for aging by due or document date, for excluding voids, and more). The trial balance comparison is stronger, because it compares GP's summary tables with a rebuild from journal lines. The AR and AP tie-out to the GL is stronger still, because the subledger and the ledger are stored independently.
- **Left out:** inventory, sales order processing, purchase order processing, payroll, fixed assets, bank reconciliation, project accounting, multicurrency, analytical accounting, third-party and custom tables, document attachments and notes (GP keeps notes in `SY03900`), and user security. Copying them is the same mechanism; reconciling them needs reports per module.
- **Scale.** About 59,000 rows in the source. A ten-year GP company with inventory and SOP can run to tens of millions of rows. DuckDB and Parquet handle that size, but we didn't measure it.
- **Dynamics NAV** is not covered. NAV's ledger tables (`G/L Entry`, `Cust. Ledger Entry`, `Vendor Ledger Entry`) are a different shape, one table per company with the company name in the table name, and would need their own export mapping and reports.
- **Bounced payments in the agings.** When GP voids a payment it removes the payment's applications. So for a date between the payment and the void, the invoice shows as open and the payment as an unapplied credit. The customer's total is right, but the buckets are not what a collector saw at the time. The archive inherits this from the data. We didn't try to correct it.

## Do partners already offer this?

Partly, and the options cost more than this demo needs. From what we found (dates are when each source was published):

- Microsoft's GP-to-Business Central cloud migration can move historical GL, receivables, payables, sales order, purchase receipt and inventory detail into Business Central extension tables as a "historical snapshot". It is free inside the migration tool. Microsoft can also copy the GP database to Azure Data Lake. [Microsoft Learn, 2026-01-14](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/migrate-dynamics-gp), [Azure Data Lake option](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/administration/cloud-migration-azure-data-lake-gp)
- eOne's Popdock sells "Access Legacy Dynamics GP Data in D365 Business Central" as a $6,000 service. It also needs a Popdock Business or Premium plan. [eOne, 2023-12-05](https://www.eonesolutions.com/blog/data-migration-services-pricing-update-on-february-5-2024/)
- Many partners recommend keeping GP running read-only, often for 12 to 24 months, on the customer's existing perpetual licence. [Alphavima, 2026-05-18](https://alphavima.com/blog/dynamics-gp-to-business-central-migration/), [ERP Software Blog, 2026-03-19](https://erpsoftwareblog.com/2026/03/migration-checklist-to-business-central/), [ArcherPoint, 2025-04-17](https://archerpoint.com/debunking-the-myths-of-migrating-from-dynamics-gp-to-business-central/)

None of the partner pages we read mentioned reconciling the archive against GP's own reports before shutdown. That is the part this demo adds. We didn't survey partners systematically, so treat this as a sample, not a market count.
